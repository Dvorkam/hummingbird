M9 — THE FETCHER

Asking the network for itself

Milestone 9 gives the page its own voice on the network: fetch(), a CORS model, and an HTTP cache — the three things that separate “the browser fetched it” from “something fetched it.” It rests on two event-loop guarantees everything promise-based needs.

The HTTP cache

A cache is invisible by nature, which is exactly what makes it hard to trust — “that felt fast” is not evidence. So this endpoint counts how many times the server was actually reached, and the page shows you that number.

Reading server counters…

The cached resource is sent with Cache-Control: max-age=10 and an ETag. Click it several times quickly: the body keeps saying served #1 and the server's full count stays at 1 — the later clicks never left the browser. The age line climbs, which is the response telling you how old it is. Now wait ten seconds and click again: full is still 1 but revalidated becomes 1. That is If-None-Match earning a 304 — the round trip happened, the payload did not, and the body you see was reused from memory. The no-store button is the control: its counter climbs every single time, because a response that says “never store this” is never stored. Added in M9 (story 9.3.1).

Reload works at the two levels a browser gives you, and this page has a cacheable stylesheet to show it with: /api/cache-demo/style.css, max-age=15, the orange bar beside the counters. Watch the stylesheet numbers and try all three:

F5 within 15s — neither stylesheet counter moves. A normal reload re-checks the document and leaves a fresh subresource alone. (Browsers used to re-check every subresource on F5 and stopped, because fifty assets meant fifty extra requests per keystroke.)
Wait 15s, then F5 — stylesheet: revalidated +1. The entry went stale, so it was confirmed with If-None-Match and a 304 reused it.
Ctrl+Shift+R — stylesheet: full +1, at any time. A hard reload ignores the cache for the page and everything on it: the answer to “I changed the stylesheet and nothing happened.”

Note which counter the hard reload moves, because it is the opposite of the intuitive guess: full, never revalidated. Revalidating means asking “is the copy I hold still good?”, and refusing to ask that is the entire point of a hard reload — so it can never earn a 304.

The API buttons above are unaffected by either reload, which is also correct: they fetch on click, long after the navigation ended. A reload sets the cache policy for the document and the subresources that load with it, not for a fetch() you fire a minute later — and it does not erase the cache. (Chrome is the same; its devtools “Empty cache and hard reload” is the one that discards entries.) Once the API entry exists, its ETag never changes, so every later fetch is either a hit or a 304 and API: full stays at 1 forever — a body fetched once and reused indefinitely, which is the cache paying for itself.

Being precise about one edge this card cannot show: a hard reload reaches the document and its subresources, but not a fetch() the page fires while it is still loading — that one is still answered from cache. Browsers do reach it, so this is a real if narrow gap (T-NET-RELOAD-FETCH-POLICY-1), not a design choice.

Responses are keyed on Vary and on whether the request carried credentials, so one URL can hold several variants and none is ever served to a request it was not negotiated for (story 9.3.2).

Declarative request filtering (ad blocking)

An extension can declare, up front, which requests the engine should refuse. The rules are matched natively in C++ at the single choke point every request passes through, so no extension JavaScript runs on the request path — a blocker cannot slow a request down or hang one, and the matching is the same on every redirect hop, which is how a tracker network would otherwise launder a blocked URL through a single redirect.

Open the ad-block demo »

Blocking is the absence of something, so it cannot be shown with pixels — the demo page states what should be missing and the log says whether it was. The bundled ad-block-lite extension is toggleable like Dark Mode, and its rules live in a plain JSON file rather than in code: a correct blocker needs no script at all. Added in M9 (stories 9.4.1, 9.4.2).

Fail-soft stubs for APIs that do not exist yet

A browser this young is missing a lot. The question is what happens when a page reaches for something absent: a ReferenceError kills the rest of that script, so one unimplemented API takes down every feature below it. Instead each known gap gets a stub that does nothing, reports itself, and above all returns.

Note what the stubs refuse to invent: the socket reports CLOSED rather than pretending to be connected, confirm() returns false because no user agreed to anything, and navigator.userAgent is empty rather than a plausible-looking lie — this engine has a real per-site identity policy (Ctrl+Shift+U), and a second answer here would contradict it.

The reporting is the point: each name is recorded once per document and written to the log as [missing-api], which is how the next milestone's scope gets chosen from what pages actually ask for instead of from guesswork. Added in M9 (T-JS-MISSING-API-COVERAGE-1, story 9.5.2).

Inline data: URLs

A data: URL carries its own bytes, so nothing should go to the network for one. Until now the loader handed them to curl anyway, which failed them as network errors — so every inline icon on a modern site cost a wasted request and rendered nothing.

window is the global object

In a browser window === globalThis — one object, not two. This engine used to build a separate window and copy a hand-picked list of globals onto it, so everything not on that list was missing: window.console, window.document, window.fetch. Real pages died on it.

Not run yet.

Identity, not merely presence: a mirrored copy would satisfy a typeof check and still be the wrong object. Because the self-reference is real, everything added to the engine later is reachable both ways for free — the old list could only ever fall behind again. A bare addEventListener now works too, and console gained the fifteen methods pages actually call (it had exactly one: log).

Found by a live log: MediaWiki's startup script died on cannot read property 'warn' of undefined — the shape of window.console.warn. Added in M9 (T-JS-WINDOW-IS-GLOBAL-1).

Routing without reloading — the History API

An API-driven page changes what it shows without fetching a new document. That needs the URL to move anyway, or Back stops working and the address bar starts lying. history.pushState adds a session-history entry; Back and Forward then fire popstate and hand the page its state back, with no reload.

The counter restarts at 1, because that is a genuine document load — and this is the part people are surprised by. A pushState URL is a real URL: once you leave the document that invented it, the address has to be served by the server like any other. Every SPA needs its host to answer sub-paths with the app’s own document (the “SPA fallback”), and the page has to read its route back out of location rather than trusting history.state, which is null on a fresh load. Both are done here, which is why the deep link shows the detail view instead of the list.
