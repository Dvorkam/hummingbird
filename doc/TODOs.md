  **CLOSED 2026-07-30, confirmed live.** The user re-ran seznam.cz on the fixed build: no crash, and the flashing
  glyphs went with it — same root cause, since the animation re-point was the window the use-after-free lived in.

  **The first hypothesis in this ticket was wrong and is left above deliberately.** "Almost certainly out of memory"
  was inferred from SDL failing on a small allocation; the follow-up log showed SDL actually reporting
  `Parameter 'pitch' is invalid`, and the bitmap "dimensions" decoded as ASCII to `"[pla"`, `"tfor"`, `"<svg"`,
  `" cla"` — the engine's own log strings and SVG source, i.e. **freed memory that had been reused**. Reading the
  garbage integers as bytes is what turned an unexplained crash into a proven use-after-free, and is worth reaching
  for early next time. Fixed by `T-RESOURCE-REF-1`, which makes the dangling reference structurally impossible rather
  than merely unlikely; the regression test mutates the store underneath a live render tree and a retained display
  list and was verified to fail before the change.

  **One aftershock, correctly diagnosed as not a regression:** a video poster then appeared to paint over article text
  on novinky.cz. The image is `position:absolute` and so never contributed to flow height, before or after; the
  container should have reserved space via `padding-top:56.25%`, which the engine does not support
  (`T-CSS-PERCENT-PADDING-1`). Making painting reliable exposed a layout gap that missing pixels had been hiding —
  expect that pattern after any rendering-correctness fix.

  **ROOT CAUSE FOUND 2026-07-30, and it is a use-after-free.** A follow-up run with the new boundary logging printed
  bitmaps with dimensions like `16908801x33620482` and `1634496603x1919903348`. Decoding those integers as bytes is
  conclusive: `1634496603` = `"[pla"` and `1919903348` = `"tfor"` — the engine's own `[platform]` log string —
  and `1735815996` = `"<svg"`, `1634493216` = `" cla"` — SVG source text. **The renderer is drawing an `ImageBitmap`
  whose memory has been freed and reused for something else.** Sometimes that memory is unmapped or yields a wild
  pointer, which is the silent termination. SDL's real complaint was `Parameter 'pitch' is invalid` — a malformed
  bitmap, NOT the out-of-memory the first pass guessed; that guess was wrong and is corrected in the log text.

  **The defect:** the render tree caches raw `const ImageBitmap*` into memory owned by `ResourceStore` —
  `RenderImage::m_image`, `RenderObject::m_background_image`, and the animation frame pointer from `current_image()`.
  The store frees those bitmaps at four points with no invalidation of anything pointing at them: `set_image` (replaces
  and frees the old), `set_animation` (`image.reset()`), `mark_failed` (resets both), and `clear()`. Any paint between
  a free and the next `update_image_resources` draws freed memory. It correlates with animated images exactly as the
  reporter observed ("animation glyphs which kept rotating") because an animation ticks every frame, so it repaints
  constantly and widens the window until it is hit.

  **The fix is shared ownership, not more checks.** Make the pixels outlive every pointer to them: `ImageRef =
  std::shared_ptr<const ImageBitmap>` held by the store, by `RenderImage`/`RenderObject`, and per animation frame, so
  a store-side free merely drops one reference. That makes the bug impossible rather than unlikely. Blast radius is 10
  files / ~54 references across `layout/`, `renderer/` and `engine/`, so it wants its own reviewed commit.

  **Manifest version: take the Firefox position, and note that MV3 is not the constraint people assume.** Chrome's MV3 replaced blocking `webRequest` with `declarativeNetRequest`; **Firefox's MV3 kept both**, which is precisely why uBO ships a full MV3 build there and only a degraded "uBO Lite" on Chrome. So the two mechanisms are **complementary, not alternatives**, and 9.4.1 does not fork the road: declarative rules are the cheap, always-on path that needs no extension JS on the network, and blocking `webRequest` would be an *additional*, permission-gated capability for extensions that genuinely need per-request logic. Adding it later is not a reversal of 9.4.1 — it is the second half of the Firefox model. What it does buy is the hazard 9.4.1 avoided by construction (arbitrary, possibly re-entrant script inside the request path, with a hang risk), so it must arrive with its own timeout/re-entrancy story rather than as a plain callback. Support the MV3 manifest shape first, since that is where maintainers are moving; treat MV2 compatibility as a separate question about *manifest parsing*, not about capability.

  **Blocking `webRequest` must sit at a HIGHER permission tier than `declarativeRequest`, and the UI must say why.** The two are not the same capability wearing different syntax, and the difference is the real security argument — worth stating plainly, because it is usually lost in the (largely justified) suspicion about Chrome's motives:
  * A declarative rule gives an extension the power to **block** a request without ever **seeing** it. The engine matches natively; the extension learns nothing about what the user loaded. That is a genuine, large privilege reduction, not a technicality.
  * Blocking `webRequest` hands the extension every URL, every request header, and the ability to inspect and rewrite bodies — for **every** request, first-party included. That is session cookies, `Authorization` headers, form posts, API payloads. An extension holding it is a network intermediary with total visibility, and it is the single most valuable thing to acquire in an extension supply-chain attack: buy a popular extension, ship one update, exfiltrate everything. That attack has happened repeatedly in the real world, which is why the argument stands on its own regardless of who is making it.
  * So the permission must be *separately named*, *separately surfaced*, and — unlike a manifest permission that is merely declared — plausibly require an explicit user opt-in, because "can block ads" and "can read all your traffic" should never be granted by the same click.

  **Where the suspicion is nonetheless correct.** The security case justifies *withholding request visibility*; it does not justify Chrome's **rule-count caps** on `declarativeNetRequest`, which are a policy choice with no confidentiality rationale and are the thing that actually degrades blockers. Our version should therefore take the security half and skip that half: no artificial rule ceiling beyond what the matcher can perform well at (see T-EXT-EASYLIST-1). Recording this so the tiering is not later justified by an argument it does not support.
