How a page becomes pixels

A clickable map of the current Hummingbird document pipeline. It follows a navigation from an HTML response through DOM, CSS, layout, and painting—and calls out the asynchronous resource updates and JavaScript mutations that send the pipeline around again.

Click a block to open its implementation notes and source links below. The vertical route is the first document pass; the two lower blocks are feedback paths, not extra linear stages.

First document pass

Navigation and I/O are coordinated by Engine::Tab. DOM, style, layout, and command recording stay on the main thread; network callbacks only queue resource updates.

Incremental resource loop

A stylesheet or font completion rebuilds style + layout. An image completion updates render objects and relayouts when its size changes.

Document script loop

External scripts defer until their resource bodies resolve. DOM mutations are batched, then trigger one style/layout/paint refresh for that task.

1. Navigation

A URL-bar action, link, history entry, or form submission reaches a Tab. The tab starts a new navigation session, clears the old document state, records navigation state, and asks the resource loader for the document.

  • Form submissions choose GET or POST through the form-submission path.
  • Each tab owns its document pipeline, resource loader, script engine, and layout state.

Key code: Tab.cppNavigationLifecycle.cppFormSubmissionBuilder.cpp

2. Document loading and the resource store

ResourceLoader first records a typed request in ResourceStore. It can serve built-in/demo assets through IResourceProvider or ask the injected INetwork port to fetch the document.

  • Network callbacks enqueue a result; they do not touch the DOM.
  • On the main-thread tick, consume_pending_updates() moves bodies, decoded images, and failures into the store.
  • A navigation ID discards late callbacks from a prior page.

Key code: ResourceLoader.cppResourceStore.cppResourceUpdateProcessor.cpp

3. HTML tokenization, parsing, and early discovery

DocumentModel hands the response body to Html::Parser. The tokenizer emits tags and character data; the parser builds arena-backed DOM nodes through DomFactory and keeps an open-element stack.

  • Inline <style> text, stylesheet links, and image sources are collected while parsing.
  • Classic script elements are collected from the resulting DOM. Script/style raw-text handling preserves their source as text rather than treating markup-looking content as HTML.
  • One document arena owns the page DOM and is bulk-reset on navigation.

Key code: DocumentModel.cppHtmlTokenizer.cppHtmlParser.cppDomFactory.cpp

4. CSS source, cascade, and computed styles

DocumentResources merges the user-agent stylesheet, ready external stylesheets, inline styles, and extension CSS. The CSS parser produces a stylesheet; StyleEngine indexes rules and walks the DOM to attach a computed style to every node.

  • Selector specificity, inheritance, media conditions, custom properties, and the supported CSS property set resolve here.
  • @font-face resolution can discover additional font requests; ready font bytes feed a later restyle.
  • Stylesheets that are still loading simply join a later incremental pass.

Key code: DocumentStyleCoordinator.cppDocumentResources.cppCssParser.cppStyleEngine.cpp

5. Render-tree construction

TreeBuilder maps visible DOM nodes and their computed display values into layout objects. Non-visual tags and display: none do not produce normal render objects.

  • Factories choose block, inline, list-item, flex, grid, table, text, image, SVG, and control render objects.
  • The render tree is separate from the DOM: it is the tree that owns page geometry and painting behavior.

Key code: DocumentModel.cppTreeBuilder.cppRenderFactory.cpp

6. Layout and positioning

DocumentRenderer calls RenderObject::layout() with the content viewport. The selected render object handles its formatting model; a second positioning pass places absolute/fixed-style supported cases. The result is a geometry tree and document content height.

  • Current specializations cover block/inline flow, text line building, flexbox, grid, tables, lists, replaced images/SVG, and controls.
  • The graphics port provides text measurement without pulling a platform implementation into layout.
  • Viewport changes can trigger a plain relayout or a restyle first when a media condition flips.

Key code: DocumentRenderer.cppRenderObject.cppBlockBox.cppFlexBox.cppGridBox.cpp

7. Display-list recording, replay, and presentation

DocumentPainter walks the laid-out render tree through Renderer::Painter. A recording graphics context turns fills, text, images, alpha, and clip operations into a DisplayList, which is then replayed into the real graphics context.

  • The display list can be reused while the render tree, viewport, scroll offset, and debug-outline mode are unchanged.
  • RenderCoordinator composes the rendered document with browser chrome and presents through the platform graphics/window adapters.

Key code: DocumentPainter.cppPainter.cppDisplayList.hRenderCoordinator.cpp

Resource loop: later CSS, images, fonts, and SVG

After parsing, the tab requests discovered external stylesheets and images. After a style pass, it also requests background images and pending web fonts. Every completion returns through the same typed resource queue.

  • Ready stylesheet → rebuild CSS, computed styles, render tree, and layout.
  • Ready font → restyle and relayout so text metrics can change.
  • Ready raster image → attach decoded bitmap to the render object and relayout if necessary.
  • Inline SVG is serialized from the DOM and decoded into a replaced image during resource update.

Key code: Tab.cppTabDocumentReadyPolicy.cppDocumentResources.cppResourceUpdateProcessor.cpp

Script loop: document-order execution and batched mutation

The parser preserves inline script text and records external script URLs in document order. External script bodies are requested before execution; when they are all resolved, DocumentScripting passes the ordered sources to the document script controller and its IScriptEngine implementation.

  • QuickJS remains behind the platform script port; the engine talks through document bindings and a script host.
  • Click, input, submit, load, timer, and animation-frame paths can dispatch into the document.
  • If a task mutates the DOM, the tab performs one subsequent style/layout rebuild rather than rebuilding once per mutation.

Key code: DocumentScripting.cppDocumentScriptController.cppDocumentScriptHost.cppQuickJSScriptEngine.cpp
